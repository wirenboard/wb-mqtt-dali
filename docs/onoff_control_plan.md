# Plan: настраиваемый контрол включения/выключения для устройств и групп

Branch: feature/SOFT-7174-onoff_control

## Контекст

Сегодня включение/выключение устройства или группы делается напрямую через существующие
низкоуровневые MQTT-контролы: `wanted_level` (проценты, через кривую диммирования),
`dapc` (сырое значение 0..254), `go_to_scene` (0..15), `go_to_last_active_level`, `off`.
Время перехода (fade time) отдельным параметром команды не передаётся — это
DALI-параметр устройства (`Fade time and fade rate`, код 0..15, ~0.7..90.5 с),
настраиваемый отдельно и применяющийся ко всем последующим командам, пока не будет
переустановлен.

Группы (0..15) на каждой шине уже существуют как виртуальные MQTT-устройства
безусловно, для каждой шины, независимо от конфига — `<device_id>_bus_<N>_group_<MM>`.
В `wb-mqtt-dali.conf` группы сегодня вообще не описываются (нет ни списка групп, ни
настроек для них) — членство в группе читается динамически с самих балластов.

Задача: добавить новый MQTT-контрол `on_off` поверх этих примитивов — для выбранных
устройств и выбранных групп, с независимо настраиваемой стратегией включения и
стратегией выключения. «Выключено» на этой итерации — ровно уровень 0 (без отдельного
настраиваемого порога).

## Сценарии

### 1. Настройка контрола для устройства

В конфиге у устройства (`bus.devices[]`) появляется необязательный блок `on_off`
с обязательными `on_action` и `off_action`. Без блока `on_off` устройство ведёт себя
как сегодня — новый контрол не публикуется.

Поля `enabled` в файле у блока нет: «включено» выражается самим присутствием блока.
`enabled` существует только в представлении Editor-RPC (см. «Требования к доработке
homeui»).

Блок применим только к классическим DALI-устройствам (control gear). Для записей с
`dali2: true` контрол не делаем — это по смыслу другие устройства; блок `on_off` на
такой записи просто пропускается: контрол не публикуется, ошибок валидации нет;
при перезаписи конфига сервисом блок не сохраняется.

Блок хранится в объекте устройства и выгружается обратно при перезаписи конфига
сервисом (`save_configuration` — после коммишининга, при старте, из Editor-RPC):
настройки переживают сканирование шины. Переживает блок и пересоздание объекта
устройства сервисом, в том числе `ResetDeviceSettings`: заводской сброс балласта
не сбрасывает сервисную настройку `on_off`.

### 2. Настройка контрола для группы

В `definitions/bus` появляется новый необязательный список `groups`, элемент —
`{"number": 0..15, "on_off": {...}}` с той же формой `on_off`, что и у устройства.
Существование самой группы как MQTT-устройства от списка не зависит (группы 0..15
публикуются всегда); `mqtt_id`/имя группы через список не переопределяются — только
настройки вкл/выкл. Список `groups`, как и блоки `on_off` устройств, переживает
перезапись конфига сервисом (см. Сценарий 1) — с одним исключением: если после
сканирования шины группа достоверно исчезла (ни один балласт больше не числится её
участником), её элемент из `groups` при перезаписи не сохраняется. «Достоверно» —
по данным инициализированных устройств: пока на шине есть неинициализированные
устройства (их членство неизвестно), записи `groups` не удаляются; удаление
логируется.

### 3. Включение (`on_action`)

`on_action` и `off_action` — плоский объект: поле `mode` и рядом, на одном уровне,
необязательные поля режимов (`scene`, `percent`, `value`, `fade_time`). `oneOf` не
используется: это обычные `object`. UI-редактор блока задаётся форматом `dali-on-off`
на объекте `on_off` в схеме, которую отдаёт Editor-RPC (статическая схема конфига —
только для валидации, без подписей и формата); зависимости полей от режима внутри
обоих действий разруливает редактор на фронте. Диапазоны полей проверяет схема (обычные min/max); всю обязательность
проверяет код — один парсер на загрузку конфига и Editor-RPC: наличие
`on_action`/`off_action` (в файле — всегда, в RPC — при `enabled: true`), наличие
`mode` и полей выбранного режима. `oneOf`/`if-then`/`required` в схеме блока не
используются; поля, не относящиеся к выбранному режиму, игнорируются.

`on_action` — один из `scene` / `last_active_level` / `level` / `dapc`. Запись `1`
в контрол `on_off` выполняет настроенный `on_action`:

- **`scene`** (`{mode, scene: 0..15}`) — `GoToScene(scene)`. Fade time отдельно не
  задаётся — используется тот, что уже установлен на устройстве.
- **`last_active_level`** (`{mode, fade_time: 0..15}`) — сначала устанавливается
  fade time (тот же код 0..15, что и у параметра `Fade time and fade rate`), затем
  `GoToLastActiveLevel`. «Последний уровень» берётся из памяти самого балласта,
  приложение его отдельно не хранит.
- **`level`** (`{mode, percent: 1..100, fade_time: 0..15}`) — сначала fade time,
  затем DAPC на уровень, пересчитанный из процента через кривую диммирования —
  то же преобразование, что уже использует `wanted_level`. Для группы кривая берётся
  так же, как сегодня для группового `wanted_level`: общая, если у всех участников
  одинаковая, иначе логарифмическая по умолчанию.
- **`dapc`** (`{mode, value: 1..254, fade_time: 0..15}`) — сначала fade time, затем
  DAPC на сырое значение без пересчёта — как сегодняшний контрол `dapc`.

### 4. Выключение (`off_action`)

Та же плоская форма, настраивается независимо от `on_action`. Уровень в
`off_action` не задаётся — оба режима гасят ровно в 0, поэтому состояние контрола
гарантированно переходит в `0`. `off_action` — один из `off` / `dapc`. Запись `0`
в контрол `on_off` выполняет настроенный `off_action`:

- **`off`** (`{mode: "off"}`) — команда DALI `Off`: мгновенное выключение, fade time
  не учитывается и не устанавливается.
- **`dapc`** (`{mode, fade_time: 0..15}`) — сначала fade time, затем DAPC на уровень
  0 — плавное гашение за настроенное время.

### 5. Fade time

`fade_time` во всех режимах `on_action`/`off_action`, где он есть, необязателен: без него команда
выполняется с текущим fade time устройства — установки и восстановления нет. Если
`fade_time` задан, то, поскольку fade time — параметр устройства, а не атрибут вызова,
после выполнения команды сервис возвращает его в значение, действовавшее до действия:
последующие вызовы `wanted_level`/`dapc` настроенный fade time не наследуют. Прежнее
значение известно из чтения параметров при старте сервиса и дальнейшего отслеживания
(свои команды и sniffed); если прочитать его не удалось, восстановление не
выполняется — остаётся fade из действия. Чтобы не изнашивать NVM балласта, запись
fade time (DTR0+SetFadeTime) пропускается, когда известное текущее значение совпадает
с целевым.

Для группы команды установки и восстановления fade time уходят на групповой адрес и
относятся ко всем участникам группы разом; восстанавливается значение активного
представителя группы — того участника, чьё состояние группа сейчас зеркалит
(см. Сценарий 6). Если прежний fade time представителя неизвестен, восстановление,
как и для устройства, не выполняется.

### 6. Запись и состояние контрола

Значение контрола — булево (`0`/`1`), выводится из уже известного/предсказанного
сырого уровня устройства (тот же уровень, что видит `actual_level`): уровень `0` →
`0` (выключено), иначе `1`.

Запись в контрол публикует новое состояние оптимистично, сразу при выполнении
действия, не дожидаясь предсказанного/опрошенного уровня — это важно для
`last_active_level` и сцены с ещё не прочитанными параметрами, где целевой уровень
заранее неизвестен, а подтверждающий опрос приходит только после окончания fade
(до ~90 с). Повторная запись значения, совпадающего с текущим состоянием контрола
(`1` при `1`, `0` при `0`), игнорируется — команды на шину не отправляются.

Дальше контрол обновляется по тому же событийному механизму, что уже обновляет
`actual_level` (включая команды, отправленные этим же контролом), — он подтверждает
или поправляет оптимистичное значение. Своих query-команд контрол не шлёт: уровень
запрашивается на шине один раз — опросом `actual_level` — и `on_off` пересчитывается
из того же ответа. Для группы состояние наследует существующий механизм зеркалирования
группового состояния (тот же, что уже используют `actual_level` и цветовые контролы
группы) — новой логики агрегации по участникам не вводится.

## API (конфиг + MQTT-контрол)

| Сущность | Расположение | Форма | Эффект |
|---|---|---|---|
| `on_off` | `definitions/device`, новый `definitions/group` | `{on_action, off_action}` | Включает публикацию контрола `on_off` для этого устройства/группы |
| `on_action` | внутри `on_off` | плоский объект: `mode` (`scene`\|`last_active_level`\|`level`\|`dapc`) + поля режимов на одном уровне; применимость проверяет код | Стратегия включения (см. Сценарий 3) |
| `off_action` | внутри `on_off` | плоский объект: `mode` (`off`\|`dapc`) + `fade_time` (уровень не задаётся — гашение всегда в 0) | Стратегия выключения (см. Сценарий 4) |
| `groups` | новый список в `definitions/bus` | `[{number: 0..15, on_off}]` | Настройки вкл/выкл для конкретных номеров групп |
| MQTT-контрол `on_off` | `/devices/<mqtt_id>/controls/on_off` | `switch`, `0`/`1`, читаемый и записываемый | Запись `1`/`0` выполняет `on_action`/`off_action`; значение: `0` при уровне 0, иначе `1` (см. Сценарий 6) |

- `README.md` — раздел «Структура конфигурационного файла» (пример блока `on_off` на классическом DALI-устройстве, не dali2, и для группы) и раздел «Топики MQTT» (упоминание нового контрола `on_off`); примечания: `on_off` — только для классических DALI-устройств; после замены балласта настраивается заново; при неизвестном прежнем fade time восстановление не выполняется; записи `groups` достоверно исчезнувших групп удаляются после сканирования.

## Требования к доработке homeui

Сама доработка ведётся вне этого репозитория (см. Out of scope); здесь — требования,
вытекающие из плана. Редактор работает через Editor-RPC (`docs/editor_rpc.md`) и
строит формы по схемам из ответов: устройство — `Editor/GetDevice`/`SetDevice`
(конфиг + JSON Schema), группа — `Editor/GetGroup`/`SetGroup`. Серверная часть этой
задачи: `GetDevice` отдаёт блок в `config` и его схему; ответ `GetGroup` приводится
к форме `GetDevice` — `{config, schema}`, где `config` несёт текущий `on_off` группы,
а `schema` — прежнее слияние схем групповых параметров (методы служебные, контракт
меняется согласованно с доработкой homeui); В RPC-представлении блок несёт булево поле
`enabled`; `GetDevice`/`GetGroup` возвращают блок всегда — для ненастроенных
устройства/группы это `{"enabled": false}`. `SetDevice`/`SetGroup` принимают блок с
сохранением в конфиг: `enabled: true` задаёт настройки, `enabled: false` удаляет их
(остальное содержимое блока при этом не валидируется и не сохраняется); в файл поле
`enabled` не пишется. Повторная запись неизменённого блока — no-op
(`{"enabled": false}` эквивалентен отсутствию блока): устройство/группа не
пересоздаются, конфиг не переписывается. Правка группового `on_off` не сбрасывает уже известное
состояние группы (retained-значения и представитель сохраняются или немедленно
восстанавливаются) и сериализуется с остальными операциями контроллера; при передаче
`on_off` вместе с параметрами балластов блок применяется и сохраняется только после
успешного применения параметров.

- У устройства: чекбокс включения `on_off` (поле `enabled` из RPC); при включённом
  чекбоксе обязательны оба действия — `on_action` и `off_action`. Снятие чекбокса
  удаляет настройки — при повторном включении форма пуста (выключенный блок в файле
  не хранится).
- У группы (0..15): та же форма `on_off`, что у устройства; имя группы и её состав
  редактируются как сегодня, через форму `on_off` не меняются.
- Новый тип редактора блока `on_off`: `format: "dali-on-off"` на объекте `on_off` в
  схеме Editor-RPC (`GetDevice`/`GetGroup`). Редактор сам разруливает зависимости полей
  от `mode` внутри обоих действий — после выбора режима показываются только его поля;
  схема зависимостей не кодирует (`oneOf` нет):
  - `on_action`: `scene` (`scene` 0..15) | `last_active_level` (`fade_time`) |
    `level` (`percent` 1..100, `fade_time`) | `dapc` (`value` 1..254, `fade_time`);
  - `off_action`: `off` (без полей) | `dapc` (`fade_time`).
- `fade_time` (0..15) во всех режимах, где он есть, необязателен и выбирается из
  списка, а не вводится голым числом. В списке: явный вариант «из настроек устройства» — должно
  быть понятно, что действие выполнится с fade time, заданным в настройках самого
  устройства (поле при этом отсутствует в конфиге, значение по умолчанию не
  подставляется), — и номинальные времена по Table 4 IEC 62386-102 («≈0,7 с (код 1)»
  … «≈90,5 с (код 15)», код 0 — мгновенно); в конфиг пишется код.
- Диапазоны и русские подписи — из схемы конфига (`wb-mqtt-dali.schema.json` и схема
  из `GetDevice`), не дублируются в UI руками; применимость и обязательность полей по
  режимам — логика нового редактора, на сервере то же проверяет код.
- Карточка устройства/группы доработки не требует: контрол `on_off` — стандартный
  `switch`, публикуемый сервисом.

## Out of scope

- Контрол вкл/выкл для broadcast-виртуального устройства — только устройства и группы, как явно запрошено.
- Контрол `on_off` для DALI-2-устройств (`dali2: true`) — не делаем: по смыслу это другие устройства (управляющие, не светильники); блок на такой записи пропускается без ошибок.
- Переопределение `mqtt_id`/`name` группы через новый список `groups` — только настройки вкл/выкл.
- Настраиваемый порог «выключенного» уровня — «выключено» жёстко означает уровень 0; порог как отдельная настройка не вводится.
- Отдельный явный override fade time для режима `scene` — DALI не передаёт время как параметр `GoToScene`, используется текущее fade time устройства.
- Применение изменений конфига без перезапуска сервиса — как и для остальных настроек `wb-mqtt-dali.conf`.
- Автоматический перенос настроек `on_off` на балласт-замену — после замены (short тот же, random другой, коммишининг заводит новую запись) `on_off` настраивается заново; фиксируется в README. Перенос настроек — отдельная задача, если понадобится.
- Доработка dali-редактора homeui под настройку `on_off` — ведётся вне этого репозитория; требования собраны в разделе «Требования к доработке homeui».
- Extended fade time (IEC 62386-102 §9.5.4) и задание fade целевым временем в секундах — отдельная задача; в этой итерации `fade_time` — только код 0..15 (сетка 0,7..90,5 с).
