# План: поддержка датчиков Helvar Digidim

Branch: `feature/soft-7797_helvar_digidim`

## Контекст

Исследование — [helvar_digidim_research.md](helvar_digidim_research.md) (протокол,
разбор Toolbox, 311) и [helvar_321_research.md](helvar_321_research.md) (321).

Сейчас (1.43.0) устройство, которое отвечает на QUERY CONTROL GEAR и молчит на QUERY
DEVICE TYPE, считается не поддерживающим DALI: не публикуется, перепроверяется раз в
час. Так ведут себя 311 и 321 в адресном пространстве светильников (102). Этот механизм
убирается: опознанные Helvar получают свои классы, а прочие молчащие на QUERY DEVICE
TYPE — обычные светильники с ошибкой инициализации, как до 1.43.0. 321 из темы
техподдержки к тому же отвечает как устройство управления 103 со своим коротким
адресом (у одного случайного адреса `0x34137c` — адреса 1/61 среди светильников и 10
среди устройств управления); там он публикуется, но событий не шлёт.

Toolbox работает с датчиками Digidim только в пространстве 102 и только кадрами FF16
и FF17 (17-битные кадры Helvar); запросов 103 в нём нет. Сервис делает так же. FF17
отправляется кодом размера кадра 3 в регистре отправки, ответ — обычный BF8, 17-й бит —
младший бит кадра, всегда 0 (так в 2589 кадрах FF17 из логов монитора WB-DALI — и от
Toolbox через интерфейс 510, и от датчиков; research, «17-й бит по монитору WB-DALI»).
Шлюз с прошивкой без FF17 кадр с кодом размера 3 не отвергает: прошивка 1.2.3 на любом
коде 3–7 отправляет младшие 16 бит как FF16, и светильники их выполняют (проверено на
стенде). Поэтому пакет с кадром FF17 уходит только на шлюз, чья прошивка (регистры
250–265) не ниже 1.3.0; иначе пакет не отправляется и все его кадры получают ошибку шлюза.
Версия читается с первым пакетом с FF17 после сброса очереди шлюза и до следующего сброса
не перечитывается; не прочиталась — читается со следующим таким пакетом. Для пусконаладки
шлюз без FF17 и молчащий датчик одинаковы — устройство не Helvar.

Устройство Helvar опознаётся только пусконаладкой — у новых и изменившихся устройств
— и помечается в конфиге признаком `"helvar_digidim": true`. Записи, уже лежащие в
конфиге, не перепроверяются и в Helvar не переводятся: единственная известная
инсталляция с 311/321 удалит их руками и найдёт заново.

Устройства Helvar Digidim публикуются в MQTT с одним контролом `error_status`: управлять
датчиками нечем, присутствие пока не делаем. Сертифицированные Helvar DALI-2
(D2) — обычные устройства DALI-2, их это не касается.

## Сценарии

### 1. Датчик Digidim в пространстве 102

**Пусконаладка.** У нового или изменившегося светильника, у которого не прочитался
GTIN из банка 0 (его и так читают ради имени), — проверка Helvar: запросы идут
пачками с обычными повторами. Чтение E2 — один пакет участков, у каждого свой DTR;
разрыв до 2 байт читается насквозь (новый участок стоит DTR и Extended DTR MSB);
повтор ставит DTR на первый непрочитанный байт участка.

1. FF17 Extended Query Major / Minor Version → версия ПО Helvar. Нет ответа или ошибка
   шлюза — устройство не Helvar.
2. DTR = 0, FF17 Extended DTR MSB = 0, 10 × FF17 Read E2 → GTIN (байты 0–6, BCD) и
   серийный номер (7–9). Нет ответа на любой из них — устройство не Helvar.
3. GTIN с префиксом Helvar (`5030797`, `6418488`) — устройство Helvar. Модель знается
   только у поддерживаемых: 311 (`5030797003118`) и 321 (`5030797003217`); остальные
   называются «Helvar» и GTIN. Иначе — не Helvar.

Прошедшее проверку устройство записывается в конфиг с признаком `"helvar_digidim":
true`, имя по умолчанию — из модели. Не прошедшее — обычный светильник.

**Работа.** Устройство с признаком публикуется в MQTT с одним контролом `error_status`
(тревога): раз в 120 с — QUERY CONTROL GEAR PRESENT, ответ YES — 0 «Норма», молчание —
1 «Не отвечает». Других запросов при старте и в фоне к нему нет. GetDevice читает с
датчика версию ПО, GTIN и серийный номер (шаги 1–2) и показывает их только для чтения
вместе с именем; у 311 и 321 — ещё настройки (сценарий 2) и вверху формы текст: датчик не
отправляет событий и не управляется командами DALI, а сам управляет другими устройствами по
состоянию своих датчиков; у остальных моделей — текст
«Устройство Helvar Digidim, работа с этой моделью не поддерживается». Датчик не
ответил — ошибка RPC.

**Идентификация, сброс, удаление.** Идентификация — INITIALISE на короткий адрес
датчика, через 5 с TERMINATE: всё это время датчик мигает светодиодом (research,
«Идентификация датчика»). Сброс настроек датчику ничего не отправляет: его настройки — в E2, а
DALI RESET их не касается. Удаление стирает короткий адрес, как у остальных устройств,
но без DALI RESET перед этим.

### 2. Настройки 311 и 321 в редакторе

Раскладка E2 у 311 (любой версии ПО) и 321 одна, схема формы одна; у модели просто
нет полей, которых нет у датчика (таблица ниже).

GetDevice читает при открытии формы (не в фоне) байты E2, из которых собраны поля
формы, и сервис запоминает этот образ. Запись — побайтная, любой отдельный байт
пишется сам по себе. SetDevice, как Toolbox, сравнивает новый образ с запомненным и
пишет только отличающиеся байты: на первый байт непрерывного участка DTR = адрес, на каждый байт
Enable Write E2 + Write E2 (адрес E2 датчик увеличивает сам). Все кадры после DTR, и
при чтении, и при записи, идут с приоритетом продолжения транзакции, чтобы чужой DTR
(датчики Digidim шлют его на событиях) не вклинился и не сдвинул адрес E2. Контрольного чтения нет,
запомненный образ обновляется записанными байтами. Имя меняется только в конфиге, как
сейчас.

В байте DIP (0x26) меняются только биты полей формы, остальные (скрытые для модели
флажки и неизвестные биты 3, 4, 6, 7) остаются как прочитаны. Остальные байты с
несколькими полями (0x0B, записи событий) целиком определяются формой.

| Поле | Значения | 311 | 311, ПО < 6.00 | 321 |
|---|---|---|---|---|
| Чувствительность | 1–9 | да | нет | нет |
| On Time | 1–85 мин, шаг 20 с | да | да | да |
| Transition | 20 с – 85 мин, шаг 20 с | да | да | да |
| Exit Delay | 1–85 мин, шаг 20 с | да | да | да |
| Датчик присутствия включён | DIP, бит 2 | да | да | да |
| ИК-приёмник пульта включён | DIP, бит 1 | да | нет | нет |
| Constant Light | DIP, бит 0 | нет | нет | да |
| Режим проверки присутствия | DIP, бит 5 | да | да | да |
| Блокировка | да/нет | да | да | да |
| Scene Store Delay | 2–25 с | да | да | да |
| Игнорировать ИК-пульт (Disable IR, 0x0E) | да/нет, пишется `F2` / `FF` | да | нет | нет |
| Код ИК-пульта (IR Address Group, 0x0C) | 0 (выкл.), 1–9, A–E | да | нет | нет |
| События Presence On / Min / Off | адресат + команда + время фейда | да | да | да |
| Constant Light Out (слот 4) | то же | нет | нет | да |
| Touch Switch Input (слот 0) | то же | да | нет | да |
| Кнопки ИК-пульта: IR Selection 1–8, Wall Panel Right / Left, On/Off, Up, Down (слоты 6–18) | то же | да | нет | нет |

Кодирование — research, «Настройки датчика в E2». Для каждого события: адресат —
короткий адрес 0–63, группа 0–15 или broadcast; команда — из простого режима Toolbox
(research, «Все команды подустройства»): команды DALI без параметра, Go to Scene 0–15,
Direct Level, Off / Min with Store Last Level, команды FF17, кнопочные (Scene Recall/Store,
Touch, «уровень или выключить», «шаг / плавно», Max/Up и т. п.), «не отправлять»; время
фейда — «не менять» или индекс 0–15 шкалы DALI. Список команд у всех событий один, только
Ramp («подстройка яркости по освещённости», пишутся байты `84 00 FE` из заводского слота 311) предлагается лишь в
Constant Light Out. Байт 1 при сброшенном бите 7 режима читается как «не менять», как в
редакторе Toolbox. Responds to Groups при смене адресата-группы ставится равным этой группе,
как делает Toolbox. Запись события вне этого набора (настроена Toolbox'ом в
расширенном режиме) показывается как «нераспознанная команда», этот пункт есть только у
такого события, и запись не перезаписывается, пока пользователь её не сменит. Так же
код ИК-пульта вне Toolbox'овского набора показывается как есть.

У полей, смысл которых не виден из названия, — описание по справке Toolbox: код ИК-пульта,
поддержание освещённости и светильники для него (флажок стоит перед ними), режим проверки присутствия (пауза
после ручного выключения сокращается до 20 с).

Байты E2, не связанные с полями формы, не пишутся, а читаются, только если лежат в
разрыве участка до 2 байт. Ошибка записи —
ошибка RPC, как у остальных устройств.

### 3. FF17 в мониторе шины

Кадры FF17 нужны только самому сервису; через Bus/SendCommand они не отправляются.
Монитор их не расшифровывает: чужие, как сейчас, — `FF17`, свои — тоже hex и `FF17`,
с ответом.

### 4. Запись DALI-2 у 321

**Пусконаладка.** Новое или изменившееся устройство управления 103, чей GTIN из банка
0 (его и так читают ради имени) — GTIN 321 без D2 (`5030797003217`): DALI-2 у 321
неполный (стандартных событий нет, настройки только командами Helvar), поэтому ему
стирается короткий адрес 103, в конфиг и в MQTT он не попадает, в лог — строка уровня
info. Не стёрся (устройство сообщает другой адрес) — тоже пропускается, в лог —
предупреждение; на следующем поиске его адрес снова виден и новым устройствам не
выдаётся. Найдённый без адреса 321 при каждом поиске получает адрес и снова его
теряет. Сертифицированные Helvar DALI-2 (321D2, 320D2, кнопки D2, 945 и др.) —
обычные устройства DALI-2.

### Устройство кода

Классы DALI-устройств (`DaliDevice`, `Dali2Device`) про Helvar не знают. Датчик Digidim —
отдельный класс устройства; создавать ли его, решается в двух местах: при загрузке
конфига (по признаку) и в пусконаладке (по результату проверки).
Объекты существующих устройств в другой класс не превращаются. Код Helvar, уже
попавший в `DaliDevice`/`Dali2Device` в этой ветке, оттуда убирается, как и механизм
1.43.0 «не поддерживает DALI» (`is_helvar`, `HelvarDigidimError`, тип `HELVAR_DIGIDIM`,
сокращённая форма, перепроверка раз в час) вместе с его тестами.

### 5. Helvar в e2e-эмуляторе

Стенда нет, поэтому эмулятор инсталляции (`e2e/emulator`) учится Helvar, чтобы
проверять сервис на нём вручную, с настоящим wb-mqtt-serial.

Доработка эмулятора (шлюз, шина, модели, их тесты и README эмулятора) производственный
код не трогает.

- **Шлюз.** Код размера кадра 3 в регистре отправки — FF17: 17 бит данных, 17-й бит
  младший. Время прямого кадра — как у FF16 плюс один бит.
- **Шина.** FF17 получают только модели Helvar (слово — данные без младшего бита);
  прочие устройства его игнорируют, как требует IEC 62386-101.
- **Модель «Helvar 311»** (сейчас отвечает только на QUERY CONTROL GEAR) дополняется:
  E5/E6 — версия ПО (по умолчанию 6.08, в профиле можно задать, например, 5.xx), Read
  E2 с автоувеличением адреса — начальный адрес берётся из DTR, который ставит обычная
  команда DTR (FF16 `A3 xx`), Extended DTR MSB, Enable Write E2 на один
  следующий Write E2, Write E2 с автоувеличением. Образ E2 по умолчанию — дамп живого
  311 (research, «Образ E2»), GTIN и серийный номер — из него, серийный номер — равный
  случайному адресу.
- **Модель «Helvar 312».** Модель Digidim, которую сервис не поддерживает: как 311, но GTIN
  `5030797003125` и версия 6.47.
- **Модель «Helvar 321».** Тот же датчик Digidim в пространстве 102 с GTIN 321 и
  заводскими значениями E2 321 (research, «Заводские значения E2»), плюс устройство
  управления 103 с тем же случайным адресом: банк 0 с GTIN `5030797003217`, компоненты
  303 и 304.

Ручная проверка на эмуляторе — не автотест: после реализации её проходит агент, затем
разработчик. Профиль — 311 с ПО 6.08 и 5.xx, 312, 321 и обычный светильник:

1. Пусконаладка находит все устройства.
2. Устройства Helvar появились в MQTT с одним контролом `error_status`, светильник —
   как обычно.
3. GetDevice даёт формы своих моделей (у 311 с ПО 5.xx — без чувствительности и
   ИК-приёмника), у 312 — «не поддерживается»; среди устройств DALI-2 321 нет.
4. SetDevice меняет On Time и событие Presence On — E2 в эмуляторе изменился ровно в
   этих байтах, биты DIP не из формы не тронуты.

## API

| Что | Изменение |
|---|---|
| Конфиг | признак `"helvar_digidim": true` у записей устройств в 102 (схема конфига) |
| Editor GetDevice / SetDevice | устройство Helvar в 102: сведения о модели, у 311 и 321 — настройки, у прочих — текст «не поддерживается» |
| MQTT | устройство Helvar Digidim — один контрол `error_status`: «Норма» / «Не отвечает» |
| Пусконаладка 103 | у 321 без D2 стирается короткий адрес 103, в конфиг он не попадает |
| Монитор шины | свои кадры FF17 — hex и `FF17` с ответом |
| Editor Identify / ResetDevice | датчик: идентификация — INITIALISE на 5 с, сброс настроек — ничего, удаление — только стирание короткого адреса |

Новых RPC нет.

## Тесты

Опознавание и поведение на фейковом драйвере шины; FF17 — через тот же драйвер.

- Пусконаладка: новый 311 (GTIN не читается, отвечает на E5/E6 и Read E2) → в конфиге
  с признаком, в MQTT — только `error_status`.
- Пусконаладка: новый светильник с GTIN → проверки Helvar нет, ни одного кадра FF17.
- Пусконаладка: не отвечает на E5, шлюз вернул ошибку на кадр FF17, Read E2
  обрывается посреди GTIN или GTIN не Helvar → без признака, как сейчас.
- Старт с 311 с признаком → в MQTT один `error_status`, к датчику только QUERY CONTROL
  GEAR PRESENT; отвечает — 0 «Норма», молчит — 1 «Не отвечает».
- GetDevice устройства с признаком: 311 — модель, версия, GTIN, серийный номер; другая
  модель Helvar — то же и текст «не поддерживается», без настроек.
- 311 с ПО ниже 6.00 → в форме нет чувствительности и ИК-приёмника, байт E2 0x20 не
  читается и не пишется.
- GetDevice 311 с дампом → настройки ИК и все слоты дампа распознаны (Scene Recall/Store,
  Touch, «уровень или выключить», Up/Step Up с фейдом 0); 321 → Ramp в Constant Light Out
  и только там, настроек и кнопок ИК нет.
- SetDevice с настройками ИК и кнопочными командами → байты, как пишет Toolbox; «сцена или
  выключить» со сценой 12 → ошибка RPC, ничего не записано; неизвестный код ИК-пульта не
  переписан.
- GetDevice 311 и 321: E2 из фейка → поля формы своей модели с правильным
  декодированием (времена в 20-секундных шагах, инверсные биты DIP, адресат-группа и
  адресат-адрес).
- SetDevice: изменено два соседних поля и одно отдельное → DTR только на начало каждого
  участка, записаны ровно эти байты; биты DIP не из формы (скрытые флажки, биты 3, 4,
  6, 7) сохранены; событие с нераспознанной записью без изменений не переписано.
- Монитор: свой кадр FF17 с ответом → строка `>> <hex> FF17 - <ответ>`.
- Пакет с кадром FF17 → в шлюз не записан, у всех кадров пакета ошибка; пакет без FF17
  уходит как раньше.
- Пусконаладка: новое устройство 103 с GTIN 321 → его короткий адрес стёрт, в конфиге
  и в MQTT его нет, в логе строка info; адрес не стёрся → то же, в логе предупреждение.
- Пусконаладка: новое устройство 103 с GTIN 321D2 → публикуется как раньше.
- Идентификация датчика → INITIALISE на его адрес, через 5 с TERMINATE.
- Сброс настроек датчика → ничего на шине, класс устройства тот же.
- Удаление датчика → короткий адрес стёрт, DALI RESET не отправлен.
- Юнит-тесты самого эмулятора (рядом с имеющимися `e2e/emulator/test_*.py`, кадры
  подаются прямо в модель шины и шлюза):
  - запись в регистр отправки с кодом размера 3 → на шину уходит 17-битный кадр;
  - DTR = n, затем несколько Read E2 → байты E2 n, n+1, …;
  - Enable Write E2 + Write E2 → записан один байт; второй Write E2 без нового Enable
    Write E2 → не записан;
  - 17-битный кадр обычному светильнику → нет ответа, его состояние не изменилось.

  он шлёт, не выяснено).
