# e2e_bus_saturation

На каждую шину одного WB-DALI, на все одновременно, идёт один непрерывный поток команд к её gear:
DAPC, `QueryActualLevel`, DAPC, `QueryActualLevel`… Кольцо шины всё время полное. Каждый запрос
должен вернуть уровень своего DAPC. Тест показывает, есть ли разрывы и сколько времени занял поток
на каждой шине.

## Запуск

На контроллере от root:

```
python3 e2e/bus_saturation/e2e_bus_saturation.py --gateway wb-dali_12
python3 e2e/bus_saturation/e2e_bus_saturation.py --profile one_gear_9600
```

| Флаг | По умолчанию | Назначение |
| --- | --- | --- |
| `--gateway <device-id>` | — | реальный шлюз, уже настроенный в wb-mqtt-serial |
| `--profile <имя\|путь>` | — | эмулятор: имя каталога из `profiles/` или путь к каталогу (со `/`) |
| `--pairs <n>` | `500` | пар DAPC + запрос на шину |
| `--keep-emulator` | off | не разбирать эмулятор в конце |
| `-d`, `--debug` | off | DEBUG-логи драйвера |

Нужен ровно один из `--gateway` и `--profile`. Скрипт берёт `wb.mqtt_dali` из своего checkout.

## Реальный шлюз

wb-mqtt-dali на время прогона останавливается и затем запускается снова, если работал. Скорость
порта — как настроено в `/etc/wb-mqtt-serial.conf`. На каждой шине нужен gear; берётся первый gear
шины из `/etc/wb-mqtt-dali.conf`. У него должно быть нулевое время затухания и минимальный уровень
не выше 128, иначе запрос вернёт не тот уровень, хотя ничего не потерялось.

## Эмулятор

Эмулятор, wb-mqtt-serial и бэкап конфигов — как описано в
[`e2e/emulator/README.md`](../emulator/README.md); wb-mqtt-dali на время прогона остановлен.
Поток начинается, когда wb-mqtt-serial опубликовал состояние шины шлюза.

| Профиль | Состав |
| --- | --- |
| `one_gear` | на порту только WB-DALI, на каждой из 3 шин один gear с адресом 0, порт 115200 |
| `one_gear_9600` | то же на 9600 |

## Поток

- Команды ставятся в драйвер шины строго по порядку, не дожидаясь ответов на предыдущие; впереди
  стоят два кольца команд.
- Уровень DAPC растёт на 1 с каждой парой по кругу от 128 до 254.
- Когда поставлен весь поток, оставшиеся команды должны получить исход за 15 с.

## Результат

Разрыв — пара, в которой запрос не вернул уровень своего DAPC: другой уровень (`wrong level`), нет
ответа (`no answer`), ошибка шлюза у DAPC или у запроса (`DAPC <тип>`, `query <тип>`) или исхода
нет за 15 с (`missing reply`).

По каждой шине печатается время от начала потока до исхода последней пары и `OK` или `FAIL` с
числом разрывов по видам; затем время, за которое отработали все шины. Код выхода 1, если на любой
шине был разрыв.
