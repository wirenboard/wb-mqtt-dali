# Plan: сохранение устройства из конфига при дубликате случайного адреса

Branch: feature/commissioning-doc

## Контекст

Сейчас при ошибке кадра на известном случайном адресе (несколько устройств
делят один случайный адрес) поиск сбрасывает короткие адреса всем носителям и
рандомизирует их. Если один из носителей — устройство из конфига, оно теряет
свою запись (missing + new): имя и `mqtt_id` пропадают, хотя физически
устройство исправно и его адреса корректны.

Ключевой рычаг: RANDOMISE между проходами действует только на устройства,
введённые в режим инициализации, а INITIALISE без адреса вводит в него только
безадресные устройства. Устройство из конфига (с коротким адресом) и невидимый
дубликат (без короткого адреса) различимы по этому признаку.

**Правило доверия**: если при ошибке кадра на случайном адресе ровно одна пара
(короткий, случайный) из конфигурации была чисто подтверждена опросом и
случайный адрес задан (не `0xFFFFFF`), устройство из конфига считается
найденным, короткие адреса носителям не сбрасываются; на рандомизацию между
проходами помечаются только безадресные носители. Иначе — сегодняшнее
поведение (сброс и рандомизация всех носителей).

## Сценарии

### 1. Невидимый дубликат случайного адреса (основной)

Конфиг: (5, X). На шине: A(короткий 5, случайный X) и B(без короткого, X).
Опрос видит только A и чисто читает X с адреса 5; подтверждение известного X
даёт ошибку кадра. Правило доверия срабатывает: A остаётся найденным как
(5, X) и на шине не трогается вообще; B рандомизируется между проходами и
находится двоичным поиском как новое устройство со свободным коротким адресом.
Итог: `unchanged=[(5,X)]`, `new=[B]`.

### 2. Дубликат с коротким адресом, скрытым за коллизией опроса

Конфиг: (5, X). На шине: A(5, X), C(7, X), D(7, Z) — случайный адрес C не
виден опросу из-за коллизии на коротком 7. Доверие срабатывает, но
рандомизация безадресных C не задевает: C продолжает делить X и остаётся
ненайденным, конфликт повторится при следующем поиске. Осознанный компромисс:
ради этого двойного совпадения (коллизия случайного адреса + коллизия
короткого) устройство из конфига не сбрасываем. D находится и сохраняет свой
короткий адрес. Итог: `unchanged=[(5,X)]`, `new=[D]`.

### 3. Случайный адрес не подтверждён опросом

Пара из конфига не подтверждена опросом (устройство не ответило или ответило
с другого короткого адреса) → доверия нет, сегодняшнее поведение без
изменений.

## API

Новых RPC и публичных функций нет. Сигнатура и контракт `smart_extend` /
`CommissioningResult` не меняются.

## Тесты

Файл `tests/test_commissioning_duplicates.py`:

- Правка существующего теста невидимого дубликата (одобрена): ожидания
  меняются на сохранение записи, имя `..._keeps_config_entry`.
- `test_hidden_short_duplicate_stays_deferred` — сценарий 2: устройство из
  конфига сохранено, скрытый дубликат остаётся ненайденным (компромисс
  зафиксирован тестом).
- `test_config_only_random_conflict_is_not_trusted` — сценарий 3: без
  подтверждения опросом — сегодняшнее поведение.

## Out of scope

- Самоизлечение сценария 2 за один запуск (перенос подтверждения известных
  устройств внутрь цикла проходов + отзыв доверия) — отклонено ради простоты;
  полный вариант сохранён в scratchpad-диффе.
- Щажение устройства из конфига при дедупликации на стадии опроса (видимые
  дубликаты) — отдельная задача из отложенного списка.
- Потеря корзин рандомизации между проходами — WON'T FIX.
- `debian/changelog` — на этапе подготовки PR.
